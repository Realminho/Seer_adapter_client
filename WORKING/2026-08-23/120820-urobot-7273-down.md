# urobot-7273-down

### 목표
- 10.8.8.8 "Adapter lost the JIBOT TCP connection; robot is unreachable" 원인 확인
- 7273 접속 불가 원인 규명

### 완료 (원인 확정 — 8/20·8/22 건과 다른 장애)
- **7273은 열려 있었음. USB/ttyUSB 문제 아님.**
  - ttyUSB0~4 정상, VIA 허브·FT4232H 정상 열거, urobot·amr-adaptor 둘 다 active
  - 부팅 10:30, 장애 발생 12:06:12경
- **에러코드가 다름**: Errno 110(ETIMEDOUT) — 이전 장애의 111(ECONNREFUSED) 아님
  → 리스너 부재가 아니라 리스너가 accept 를 안 함
- **핵심 증거 (12:12~12:13 실측)**
  - `LISTEN 6 0 0.0.0.0:7273 jarvis-g pid=6330 fd=60`
    → accept 대기 큐에 6개 적체, backlog=0. 새 SYN 드롭됨
  - `SYN-SENT 10.8.8.8:45914 -> 10.8.8.8:7273 python pid=248661`
    → 어댑터 connect 가 SYN-SENT 로 130초 매달리다 ETIMEDOUT
  - `ESTAB 192.168.101.61:7273 <- 192.168.101.107:52528 Send-Q=41867`
    `ESTAB 192.168.101.61:7273 <- 192.168.101.107:56082 Send-Q=23272`
    → 2초 간격 재측정에도 Send-Q 전혀 안 줄어듦 = .107 이 안 읽음 (ping 은 응답 2ms)
  - `/proc/6330/task/6995/wchan = sk_stream_wait_memory`
    → jarvis-g 스레드 하나가 블로킹 send() 로 정지. 소켓 버퍼 찰 때까지 대기
  - CLOSE-WAIT 5개 (10.8.8.8:7273 서버측, Recv-Q 1756~1867) = 이전 어댑터 접속분 미회수
  - jarvis-g fd 73개 중 소켓 65개
- **인과 사슬**
  1. wlan0 클라이언트 192.168.101.107 이 7273 데이터를 안 읽음 (앱 멈춤/네트워크 스톨)
  2. jarvis-g 가 블로킹 send() 로 정지 (sk_stream_wait_memory)
  3. accept 루프 굶음 + CLOSE-WAIT 소켓 미회수로 클라이언트 슬롯 잠식
  4. 어댑터 SYN 드롭 → ETIMEDOUT → VEHICLE_LINK_LOST
- 12:06:22 어댑터 "no data for >10s" 감지, 이후 5초 주기 재접속 전부 110 실패

### 어댑터 로그 타임라인

## 2차 장애 22:39 부팅 — **낮 건과 다른, 기존 USB 열거 실패 재발**

### 판정 근거 (22:45 실측)
- 어댑터 에러 **Errno 111 (ECONNREFUSED), 3ms 즉시 거부** → 리스너 자체 부재
  (낮 12시 건은 110/ETIMEDOUT = 리스너는 있고 accept 굶음. 완전히 다른 장애)
- `ss -ltn sport = :7273` → 결과 없음. jarvis-g 프로세스 없음
- `/dev/ttyUSB*` 전무. `lsusb` → 루트 허브 6개만 (VIA 허브·FT4232H·RTL8152 전부 미열거)
- 커널로그 이번 부팅 `usb 1-1` 라인이 **단 1줄**:
  `22:39:07 usb 1-1: new high-speed USB device number 2 using xhci-hcd`
  → 이후 "New USB device found" 없음, 에러 로그도 없음. 디스크립터 단계에서 **조용히 정지**
  (8/22 14:30 부팅과 동일 패턴: "감지됐으나 열거 정지")
- `urobot-start: serialOpen(): cannot open serial port. No such file or directory` 반복
- eth01/eth02(RTL8152 2개)도 같이 소실 → 192.168.2.10 없어짐. 같은 허브 뒤라서 동반 소실
- ssh 는 살아있음: eth0(10.8.8.8)는 SoC 내장 rk_gmac-dwmac, USB 계통과 무관

### 워치독 — 이번에도 못 고침 (예상된 결과)
- `/usr/local/sbin/urobot-watchdog.sh` **부재**. 배포된 건 여전히 구버전
- 22:43:08 `7273 not listening (state=active) — restart #1/3 of urobot`
  → urobot 재시작만 반복. USB 열거 실패에는 무효한 조치
- `/run/urobot-watchdog.count` = 2. 3 되면 포기 래치 걸림
- **8/22 세션에서 만든 xhci 재바인드 개선판이 아직 미배포인 게 그대로 드러남**

### 복구 방법 (8/22 21:14 검증됨, 재부팅 불필요)
```
sudo sh -c 'echo xhci-hcd.5.auto > /sys/bus/platform/drivers/xhci-hcd/unbind; sleep 3;
            echo xhci-hcd.5.auto > /sys/bus/platform/drivers/xhci-hcd/bind'
# 10초 대기 후 ls /dev/ttyUSB* 확인 → 나오면
sudo systemctl restart urobot
```
- sudo 비번 필요 (ucore NOPASSWD 없음)
- ssh 경로는 eth0 라 unbind 해도 안 끊김

### 배포 스크립트 사전 검증 (22:5x, 저장소 코드 확인)
- `install-remote.sh`가 동일 유닛 경로에 `install` → `daemon-reload` → `enable --now timer`
  → 구 유닛 교체됨. 타이머 중복 안 생김. 구 래치(count/gaveup/rebinds) 제거함
- 설치 시 `systemctl start urobot-watchdog.service`는 일부러 안 함 → 타이머 첫 발화 대기
- 신 스크립트 판정: `serial_ok()` = ttyUSB 개수 >= MIN_SERIAL(4).
  현재 상태 = ttyUSB 0개 → `rebind_xhci` 분기 진입 → 성공 시 `restarting urobot`
  → **이번 장애는 신 워치독이 배포돼 있었으면 자동 복구됐을 케이스**
- 단, 낮 12시 건(110/accept 굶음)은 신 워치독도 못 잡음. 리스너 존재만 보므로 통과함
