# docking-no-motion

### 목표
- docking 시 소리·상태만 바뀌고 로봇이 움직이지 않는 원인 규명

### 지금
- 원인 확정. 수치까지 실측함. 해결책 선택만 남음

### 결론
**충전기가 UmDock 을 쏜 위치에서 2.66m 떨어져 있는데, JIBOT 의 리플렉터 포착 범위는
약 1.3~1.4m 임. 범위 밖이라 JIBOT 이 ModeCharge 로 들어가고도 한 발짝도 안 움직임.**

- 어댑터·주행 계통 버그 아님. 코드는 설계대로 동작함
- 7_01CH 규칙의 전제("접근 노드에 이미 도착해 있으니 제자리 dock")가
  이 현장 배치에서 성립하지 않는 것이 원인

### 실측 근거 (2026-08-23 22:58~23:06, HN-SH6-TR-001 / 10.8.8.8)

**1. UmDock 후 포즈가 완전히 정지**
- 22:59:16.684 `[JIBOT TX] command=UmDock params={}`
- 22:59:17 `mode=Stop status=Stopped pos=(109415, 9897, 0)`
- 22:59:22 ~ 23:00:33 **`mode=ModeCharge status=nrunto 7`, pos 가 76초간
  `(109415, 9897, 0)` 에서 1mm 도 안 변함**
- → JIBOT 이 모터를 아예 안 돌림. 접근을 시작했다가 멈춘 게 아님

**2. 충전기 좌표 역산 (gap 삼각측량, 3표본 일치)**
| 시각 | pos | gap(7_01CH) | 역산 X |
|---|---|---|---|
| 23:05:35 | (111066, 9894) | 1003.1 | 112068 |
| 23:05:40 | (111572, 9919) | 498.4 | 112070 |
| 23:05:45 | (111957, 9934) | 116.2 | 112073 |

→ **7_01CH ≈ (112070, 9940)**
- p47 목표 (109413, 9882) → 7_01CH = **2658 mm**
- UmDock 발행 위치 (109415, 9897) → 7_01CH = **2655 mm**
- UmDock 발행 위치는 p47 목표에서 **15mm**. 정위치 도착이었음

**3. 리플렉터 포착 범위 실측 = 약 1.3~1.4m**
23:05 에 수동 주행으로 충전기에 접근시켰을 때 상태 전이:
| 시각 | pos | status | 충전기까지 |
|---|---|---|---|
| 23:05:27 | (110664, 9879) | `nrunto 7` | 1406 mm |
| 23:05:32 | (110773, 9878) | **`ref`** | 1297 mm |
| 23:05:37 | (111262, 9905) | `ref` | 808 mm |
| 23:05:42 | (111779, 9929) | `ref` | 291 mm |

→ 1406mm 에선 `nrunto`(대기), 1297mm 에서 **`ref`(리플렉터 접근)로 전환**되고
  그때부터 JIBOT 이 스스로 주행함. 포착 문턱은 그 사이 어딘가
- 즉 **`nrunto` = 리플렉터를 못 찾아 대기 중, `ref` = 찾아서 진입 중**
- 이때 UmDock 을 새로 쏜 적 없음. 23:02:24 UmDock 이후 ModeCharge 가 유지된 채
  거리만 좁혀지자 알아서 `ref` 로 넘어감 → **거리 하나가 변수임을 확증**

**4. 리플렉터 접근은 정상 동작함**
- 23:05:42 에 충전기까지 291mm, 23:05:45 에 116mm 까지 스스로 들어감
- 23:05:45.720 사용자 cancelOrder → UmStop → **116mm 남기고 중단됨**
- 그대로 뒀으면 도킹 성공했을 가능성이 높음

**5. 왜 에러도 안 났나**
- `[dock] fail_timeout_sec = 200.0`
- 실제 대기 시간은 76초(22:59:16→23:00:32), 17초(23:02:24→23:02:41)
- → `JIBOT_DOCK_FAILED` 가 뜨기 전에 사용자가 취소함.
  그래서 "소리 나고 상태만 바뀌고 아무 말 없음" 으로 보인 것

### 설정 현황
- `[[motion_rules]] to = "7_01CH", mode = "dock"` — `approach` 없음, `approach_params` 없음
- `[dock.approach_params]` 블록 전체 주석 처리 → **bare UmDock** (`params={}`)
- 역방향 `{ to = "p47", from = "7_01CH", mode = "move", distance = -1900 }`
  → 설정상 1900mm 인데 실측 실거리는 2658mm. **이 값도 759mm 어긋나 있음**
  (move 후 goto 폴백이 나머지를 덮어서 지금까지 문제가 안 드러난 것)
- 오더의 dock 노드에 좌표 없음: `node seq=6 id=7_01CH ... position=None`
  → 어댑터가 UmGoto 로 접근할 수단 자체가 없음
- 실행된 코드 분기는 `_run_dock` (adapter_jibot.py:5884). 설계대로 "제자리 dock"

### 이력
- 저널(8/21 14:08~)에서 어댑터 UmDock 은 오늘 22:59:16, 23:02:24 **2회뿐이고 둘 다 실패**
- 과거 충전 성공(13:05:47, 17:31:56, 18:4x)은 전부 어댑터 UmDock 경유가 아님
- 단, 다른 현장/호기에서는 이 경로가 성공한 기록 있음
  (WORKING/2026-08-12 `15:58:42 UmDock → 15:59:30 충전`)
  → **코드 결함이 아니라 7_01CH 배치/설정 문제**

### 해결책 후보
1. **p47 보다 충전기에 가까운 접근 노드를 만들고 `approach` 로 지정**
   (`{ to = "7_01CH", mode = "dock", approach = "<새 노드>" }`)
   — 가장 정공법. FMS 맵에 노드 추가 필요
2. **`approach_params = { goal = "7_01CH" }`** 로 UmDock 에 목표를 넘겨봄
   — `UmDock` 은 `goal` 파라미터를 지원함(client.py:95). JModeCharge::Start 가
   goal 을 받으면 스스로 주행하는지는 **미검증**. 한 번 쏴보면 답 나옴
3. p47→7_01CH 를 `mode="move" distance≈+1400` 으로 먼저 붙인 뒤 dock
   — 규칙 조합이 필요해서 코드 손봐야 할 수 있음
